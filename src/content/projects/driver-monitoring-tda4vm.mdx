## In one paragraph

A driver monitoring system has to tell, from a camera pointed at the driver, whether the driver is focused, distracted, sleepy or drowsy, and it has to do this in real time on a small computer inside the car. Our team built such a system on a BeagleBone AI-64, a board based on the TI TDA4VM vision SoC. The first working pipeline ran at under one frame per second. By moving image work onto the SoC's dedicated hardware and removing work the system did not need, we brought it to 17 to 20 frames per second at about 90% accuracy. The work was published at IEEE MIUCC 2024.

## Problem

The system watches the driver through an infrared camera and classifies the driver's state from four cues: eye closure, gaze direction, yawning and head pose. For a warning to be useful it must come quickly, so the whole chain from camera to decision has to run continuously at a usable frame rate on an embedded board, not on a desktop GPU.

## Constraints

- **Heterogeneous SoC.** The TDA4VM has general-purpose CPU cores, an image signal processor (ISP) and C66x DSPs. Performance depends on putting each step on the right block.
- **Camera bring-up.** An IMX219 infrared sensor connected over MIPI CSI-2, which had to be made to work under embedded Linux before anything else could run.
- **A slow start.** The first end-to-end pipeline ran at under one frame per second.
- **Testing without the board.** Development and regression testing could not depend on having the hardware and a driver in front of the camera.

## Approach

**Camera first.** The IR sensor was integrated over MIPI CSI-2 and V4L2 on embedded Linux, using device-tree overlays and the matching drivers, so the camera appeared as a normal video device.

**Build the pipeline on the hardware blocks, not around them.** The pipeline was built with GStreamer and TIOVX, TI's implementation of the OpenVX standard. Image signal processing runs on the ISP and pre-processing runs on the C66x DSPs, so the CPU cores are left for the parts that need them.

<Figure caption="The pipeline from camera to driver state. The highlighted stages run on the ISP and the C66x DSPs instead of the CPU." wide>

</Figure>

**Test without the board.** We built an x86 software-in-the-loop environment that simulates the TDA4VM cores, the imager and the DSPs. A recorded dataset replaces the live camera, so the same application can be tested in CI and measured against known data.

## The hard part

**Symptom.** The first working pipeline produced under one frame per second: correct results, far too late to warn a driver.

**How we found it.** We profiled the pipeline stage by stage to see where the time went.

**Fix.** Three changes on top of the hardware offload: process only one face per frame (the driver), bypass frames the system did not need to analyse, and stop writing frames out during normal operation. Together with moving pre-processing to the ISP and DSPs, this brought the system to 17 to 20 frames per second.

## Result

- 17 to 20 frames per second on the BeagleBone AI-64, up from under 1.
- About 90% accuracy in classifying the four driver states.
- A software-in-the-loop environment for CI and dataset-based testing.
- Published: *Optimizing Driver Monitoring System Performance on TI-TDA4VM Edge Device*, M. A. Fathy, A. Ramadan, A. Mamdouh, A. Emad, N. Atia, M. Ghareeb, A. Aboelkheir. 2024 International Mobile, Intelligent, and Ubiquitous Computing Conference (MIUCC), IEEE. DOI [10.1109/MIUCC62295.2024.10783523](https://doi.org/10.1109/MIUCC62295.2024.10783523).

## What I learned

On a heterogeneous SoC, the first question is not "how do I make this code faster" but "which block should this step run on". The second lesson was to measure before optimising: the largest gains came from removing work the system did not need, which profiling made obvious.
